# Digging Market — 셀러/소비자용 웹앱

플리마켓 현장에서 QR로 접속해 쓰는 결제 없는 등록/발견 도구입니다.
셀러는 사진을 올리면 AI가 카테고리·설명 초안을 잡아주고, 소비자는 피드를 구경하다 찜하고
셀러에게 연락(외부 채널)해서 거래를 마무리합니다.

## 화면 구성

- `/` — 랜딩 (행사 정보 + 구경하기 진입)
- `/sell?token=...` — 셀러 상품 등록 (사전 등록된 토큰 필요, QR로만 접근). 판매 방식 선택: 고정가 / 경매
- `/my?token=...` — 셀러 본인 상품 관리 (수정/삭제/상태변경, 낙찰자·구매자 연락처 확인)
- `/feed` — 소비자 피드 (카테고리 필터, 찜, 상세보기, 셀러 연락, 입찰, 즉시구매, 내 입찰·구매)
- `/dashboard` — 운영자용 검증항목 대시보드
- `/admin` — 관리자용 셀러 등록 + QR 발급 (외부 공유 금지)

## 홈 화면에 추가 (PWA)

바이닐 레코드 아이콘으로 파비콘과 홈 화면 아이콘을 이미 넣어뒀습니다. 별도 앱스토어 설치 없이:
- **iOS**: Safari에서 사이트 접속 → 공유 버튼 → "홈 화면에 추가"
- **Android**: Chrome에서 사이트 접속 → 메뉴(⋮) → "앱 설치" 또는 "홈 화면에 추가"

추가하면 홈 화면에 아이콘이 생기고, 탭하면 주소창 없이 전체화면으로 열립니다.
아이콘을 바꾸고 싶으면 `static/icons/`, `static/favicon*` 파일을 같은 크기로 교체하면 됩니다
(icon-192.png, icon-512.png, apple-touch-icon.png는 정사각형, favicon.ico는 16x16/32x32 포함).


## 로컬 실행

```bash
pip install -r requirements.txt --break-system-packages
uvicorn main:app --reload --host 0.0.0.0 --port 8000
```

브라우저에서 `http://localhost:8000` 접속.

## AI 이미지 분석 활성화 (선택)

환경변수 `ANTHROPIC_API_KEY`를 설정하면 Claude Vision으로 실제 이미지 분석을 합니다.
설정하지 않으면 파일명 기반의 단순 규칙으로 폴백해 개발/데모는 계속 가능합니다.

```bash
export ANTHROPIC_API_KEY=sk-ant-...
```

## Render 배포

1. GitHub에 이 폴더를 push
2. Render 대시보드 → New Web Service → 리포지토리 연결
3. Build Command: `pip install -r requirements.txt`
4. Start Command: `uvicorn main:app --host 0.0.0.0 --port $PORT`
5. (선택) AI 분석 쓰실 거면 Environment → `ANTHROPIC_API_KEY` 추가
6. 행사 당일에는 Starter 플랜(월 $7)으로 잠깐 올려서 슬립모드(15분 비활성 시 대기) 방지 권장

### 중요: 데이터 유실 방지 (Persistent Disk 설정)

Render는 기본적으로 파일시스템이 임시(ephemeral)라서, **디스크를 안 붙이면 재배포/재시작마다 DB와 업로드된 사진이 전부 사라집니다.**
Starter 이상 플랜에서만 디스크를 붙일 수 있으니, 행사 기간에는 반드시 아래를 설정하세요.

1. 서비스가 Starter 플랜인지 확인 (Free 플랜은 디스크 연결 불가)
2. 서비스 페이지 → **Disks** 탭 → **Add Disk**
3. Mount Path에 `/var/data` 입력, 용량은 1GB로 충분
4. 서비스 → **Environment** 탭 → 환경변수 추가:
   - Key: `DATA_DIR`
   - Value: `/var/data`
5. 저장하면 자동으로 재배포되고, 이후부터 DB(`digging_market.db`)와 업로드된 사진이 `/var/data`에 저장되어 재배포/재시작에도 유지됩니다

`DATA_DIR`을 설정하지 않으면 (로컬 개발 시처럼) 프로젝트 폴더에 그대로 저장됩니다 — 로컬 테스트에는 영향 없습니다.

행사 끝나면 Starter 플랜과 디스크를 다시 내리셔도 됩니다 (그 전에 대시보드에서 데이터 백업 권장 — DB 파일은 Shell에서 다운받거나, `/api/stats`, `/api/items` 응답을 미리 저장해두는 것도 방법입니다).

## 데이터

SQLite 파일(`digging_market.db`)에 저장됩니다. 이미지는 `uploads/` 폴더에 저장됩니다.
행사 하루~일주일짜리 용도로는 이 구성으로 충분하며, 별도 DB 서버가 필요하지 않습니다.

## 경매 / 즉시구매

### 규칙

| 항목 | 규칙 |
|---|---|
| 판매 방식 | 셀러가 등록할 때 **고정가**(즉시구매) 또는 **경매** 선택 |
| 고정가 즉시구매 | 선착순 1명. 구매되면 `예약중`으로 바뀌고 구매자 연락처가 셀러에게 전달됨 |
| 경매 기간 | 10분 / 30분 / 1시간 / 2시간 / 4시간 / 1일 / 3일 |
| 첫 입찰 | 시작가 이상 |
| 최소 입찰 단위 | 현재가 1만원 미만 500원, 5만원 미만 1,000원, 10만원 미만 2,000원, 그 이상 5,000원 |
| 경매 즉시구매 | 즉시구매가(선택)를 정했다면 **첫 입찰 전까지만** 가능 |
| 스나이핑 방지 | 마감 3분 이내 입찰 시 마감을 그 시점부터 3분 뒤로 연장 |
| 입찰 취소 | 불가 (insert-only 기록) |
| 마감 | 입찰 있으면 최고 입찰자 낙찰(`예약중`), 없으면 `유찰` |
| 셀러 제약 | 진행 중 경매의 상태 변경 불가, 입찰 후 시작가 변경·삭제 불가, 낙찰된 경매는 다시 판매중으로 못 돌림 |
| 거래 취소 | 고정가 상품을 셀러가 다시 `판매중`으로 바꾸면 해당 거래는 취소 처리 (구매자 노쇼 대응) |

결제는 여전히 앱 밖에서 진행합니다. 앱이 하는 일은 **누가 얼마에 사기로 확정됐는지**를 정하고 양쪽에 연락 수단을 전달하는 것까지입니다.

### 구매자 식별

소비자는 로그인이 없으므로, 처음 입찰·구매할 때 브라우저에서 익명 토큰(`buyer_token`)을 만들어 localStorage에 저장하고 닉네임과 연락처를 함께 받습니다.
- 다른 사람에게는 닉네임 첫 글자만 보이고(`레****`) 연락처와 토큰은 공개 응답에 포함되지 않습니다.
- 낙찰·구매가 확정된 경우에만 셀러 본인 화면(`/my`)에 구매자 닉네임과 연락처가 표시됩니다.
- **한계**: 계정이 없으므로 한 사람이 브라우저를 바꿔 여러 명인 척 입찰하는 것(셀프 입찰로 가격 띄우기)을 막을 수 없습니다. 실서비스라면 휴대폰 본인확인 같은 식별 수단이 필요합니다.

### 동시성 처리

같은 상품에 입찰·즉시구매가 동시에 들어와도 결과가 하나로 수렴하도록 3단계로 막습니다.

1. **`BEGIN IMMEDIATE` 트랜잭션** (`write_tx`) — 트랜잭션 시작 시점에 쓰기 락을 잡아 '읽기 → 규칙 검증 → 쓰기' 사이에 다른 쓰기가 끼어들지 못하게 합니다.
2. **`version` 조건부 UPDATE (낙관적 락)** — 모든 상태 변경은 `WHERE id = ? AND version = ?`로 갱신하고 영향받은 행이 0이면 409로 실패시킵니다. SQLite에서는 1번 때문에 실제로 실패할 일이 거의 없지만, 행 단위 락을 쓰는 DB(Postgres 등)로 옮겨도 같은 코드가 그대로 안전하게 동작하도록 넣었습니다.
3. **부분 유니크 인덱스** — `orders(item_id) WHERE status != 'canceled'`. 애플리케이션 로직에 버그가 생겨도 한 상품에 유효한 거래가 2건 생기는 건 DB가 거부합니다.

### 마감 처리 (lazy close)

백그라운드 스케줄러 대신, 목록/상세/입찰/구매 요청이 들어올 때 마감 시각이 지난 경매를 확정합니다. Render 인스턴스는 잠들거나 재시작될 수 있어 앱 내부 타이머를 믿을 수 없기 때문입니다. 마감할 경매가 없으면 락 없이 조회 1번으로 끝납니다.
아무도 접속하지 않는 동안에는 DB 상태가 `available`로 남아 있지만, 누군가 보는 순간 확정되므로 사용자 입장에서 차이가 없습니다.

### API

| Method | Path | 설명 |
|---|---|---|
| POST | `/api/items` | 등록 (`sale_type`, `auction_minutes`, `buy_now_price` 추가) |
| POST | `/api/items/{id}/bids` | 입찰 `{buyer_token, buyer_name, buyer_contact, amount}` |
| POST | `/api/items/{id}/buy-now` | 즉시구매 `{buyer_token, buyer_name, buyer_contact}` |
| GET | `/api/items/{id}/bids?buyer_token=` | 경매 현재 상태 + 입찰 기록 (상세 화면 5초 폴링용, 조회수 증가 없음) |
| GET | `/api/buyers/{buyer_token}/activity` | 내가 입찰·구매한 상품과 내 상태 (`leading`/`outbid`/`won`/`bought`/`lost`) |
| GET | `/api/sellers/{token}/items` | 기존 응답 + `order`(구매자 닉네임·연락처) |

입찰 금액 부족, 이미 마감, 다른 요청이 먼저 반영됨 같은 경쟁 상황은 `409`, 잘못된 입력은 `400`입니다.

### 테스트

```bash
pip install -r requirements.txt pytest httpx
pytest -q
```

규칙 검증과 함께 동시성 테스트가 들어 있습니다: 30명 동시 즉시구매 → 정확히 1명 성공, 같은 금액 20건 동시 입찰 → 1건만 반영, 입찰과 즉시구매가 동시에 들어와도 둘 다 성공하는 일 없음, 마감 처리가 동시에 여러 번 돌아도 주문 1건, 기존 DB 마이그레이션.
락을 제거한 버전으로 돌리면 동시성 테스트 5개가 모두 실패하는 것을 확인했습니다 (테스트가 실제로 경쟁 상황을 잡아낸다는 검증).

### 기존 DB 마이그레이션

이미 운영 중인 `digging_market.db`가 있어도 서버 시작 시 `items`에 컬럼을 `ALTER TABLE`로 추가하고 `bids`, `orders` 테이블을 만듭니다. 기존 상품은 모두 `고정가`로 취급되어 바로 즉시구매가 가능해집니다. 배포 전에 DB 파일 백업을 권장합니다.

## 스코프 밖 (의도적으로 뺀 것)

- 결제/정산 기능 — 거래는 셀러 연락처(인스타/오픈채팅)로 넘어가서 앱 밖에서 진행 (낙찰·즉시구매도 동일)
- 실시간 푸시(WebSocket/SSE) — 경매 상세 화면은 5초 폴링. 추월당해도 앱을 열어야 알 수 있음
- 미결제·노쇼 낙찰자 패널티, 차순위 낙찰
- 회원가입/로그인 — 소비자는 로그인 없이 바로 이용(입찰 시 닉네임·연락처만 입력), 셀러도 이름만 입력
- 부스 배치 편집기 — 부스 번호는 텍스트로만 입력, 배치도는 현장에 별도 게시
